# Handoff Manifest — active execution handoffs (single source of truth)

Machine-readable index of all active execution handoffs. Most rows hand off to **Sophia**
(the autopilot), who updates them when she starts, resumes, or completes one. Rows may also
target another runner — e.g. the **`nelanco-claude`** interactive box — in which case the
row says so explicitly in its title. Whoever executes updates the row.

**This file is the single source of truth for handoff state**, including Telegram
topic/thread linkage (consolidated 2026-07-18 — see
`plans/HANDOFF_REGISTRY_CONSOLIDATION_PLAN.md`). `sophia/SOPHIA_HANDOFFS.md` no longer
carries a duplicate registry table; it holds only the Sophia-specific trigger protocol (GO
convention, trigger template, thread-management rules).

**Protocol for all LLMs:**
1. Before acting on any handoff, `git pull` agentic_ai_context remote `main` to get the latest plans.
2. Check this manifest — it is the only table you need for status, resume state, and Telegram linkage.
3. For the Sophia trigger protocol (how to ping her, the GO convention, thread rules), see `sophia/SOPHIA_HANDOFFS.md`.
4. Optional: run `python3 scripts/validate_handoff_manifest.py` to check this file's structural consistency (schema, duplicate rows, thread_id reuse) before relying on it.

## How to update

When Sophia (or any runner) starts, resumes, or completes a handoff, she updates the
relevant row's **Status**, **Telegram topic**, **message_thread_id**, **Resume tracker
state**, and **Last manifest update** columns and commits this file to `main`. Optionally
run `python3 scripts/validate_handoff_manifest.py` first to catch schema/consistency issues
before committing.

The **`Discord channel id`** / **`Discord thread id`** columns track a handoff whose
conversation also runs in a Discord channel (`dc:{guild}:{channel}` sessions — see
`AUTOPILOT_CHANNEL_INTEGRATIONS.md` §2 for the venue registry and channel ids). Populate
them for any row whose work is coordinated in Discord; leave blank for Telegram-only rows.

**Active supervision** — *who is driving a thread right now* — is tracked separately in
`handoffs/active_supervision.json`, not in this table. A supervisor adds an entry to its
`claims` list when it starts actively driving a thread and removes it when it stops (a small,
self-mergeable docs-only PR), so a claim never becomes a heavyweight edit against this manifest.
`scripts/build_handoff_index.py` merges each claim into the index's `supervised_by` field, marking
it stale past ~60 minutes (§2.6 of `plans/SPRINT_TRUESIGHT_ME_BOARD_PROPOSAL.md`).
